# Database

Postgres (Drizzle ORM) for **platform data**: accounts, player data, submissions. Public game data
stays in `data/*.json` — the API serves it with or without a database.

## Layout

| Path | What |
|---|---|
| `lib/db.js` | The shared handle: `getDb()`, `checkDb()`, `closeDb()`, `openDatabase(url)`. Small pool, timeouts (`POOL_DEFAULTS`). |
| `features/<name>/schema.js` | A feature's Drizzle tables |
| `db/schema.js` | Registry re-exporting every feature's tables (checked by `db/schema.test.js`) |
| `db/migrations/` | SQL migrations generated by drizzle-kit — **committed**, never edited after they've run |
| `scripts/db-migrate.mjs` | Applies pending migrations; advisory-locked; Railway pre-deploy command |
| `drizzle.config.js` | drizzle-kit config |

Rules: only a feature's `store.js` (and `schema.js`) import `lib/db.js` — services call stores. Personal data
is always read and written for the user in the request context, never a user ID passed as an argument.

## `DATABASE_URL`

| Value | Use |
|---|---|
| `${{Postgres.DATABASE_URL}}` (Railway variable reference) | Production — the **private** network URL |
| `postgres://…` | Local Postgres |
| `pglite://.pglite` | Local development with **no Postgres server** (in-process, file-backed; `.pglite/` is git-ignored) |
| `pglite://memory` | Throwaway in-memory database |
| unset | No database: game-data API works, DB-backed features return `503`, `/health` shows `database: not_configured` |

## Changing the schema

```bash
# 1. edit features/<name>/schema.js (and export it from db/schema.js)
npm run db:generate        # writes db/migrations/NNNN_*.sql — review it, commit it
npm run db:migrate         # apply locally (DATABASE_URL in .env)
npm test                   # migrations apply cleanly from scratch; schema registry is complete
```

Never use `drizzle-kit push` against production, and never edit a migration that has already run —
add a new one.

## Railway setup (one-time)

1. **API service → Variables:** `DATABASE_URL = ${{Postgres.DATABASE_URL}}` (private URL; never `DATABASE_PUBLIC_URL`,
   which is billed as egress).
2. **API service → Settings → Deploy → Pre-deploy command:** `npm run db:migrate`. A deploy only starts after
   its migrations succeed.
3. **Postgres → Settings → Networking:** keep the public TCP proxy **off** except while you need `psql`.
4. **Postgres server settings** (applied once with `ALTER SYSTEM`, one statement at a time in the Query tab,
   then a restart — they live on the volume, outside migrations):

   ```sql
   ALTER SYSTEM SET shared_buffers = '64MB';
   ALTER SYSTEM SET max_connections = 20;
   ALTER SYSTEM SET work_mem = '4MB';
   ALTER SYSTEM SET maintenance_work_mem = '32MB';
   ALTER SYSTEM SET effective_cache_size = '256MB';
   ALTER SYSTEM SET max_parallel_workers_per_gather = 0;
   ALTER SYSTEM SET autovacuum_max_workers = 2;
   ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
   ```

5. **Cost controls** (target < $4/month on the Hobby plan): replica limits 0.5 vCPU / 512 MB for Postgres and
   the API; usage email alerts at $3 and $4; backups on with short retention.

The app's pool (`POOL_DEFAULTS` in `lib/db.js`) matches this: at most 5 connections, a 5 s statement timeout,
idle connections closed after 30 s.

## Testing

- `npm test` uses PGlite (in-process Postgres) — no server or secrets needed, works in CI.
- `db/postgres.test.js` covers what PGlite can't (the node-postgres pool, session settings, the migration lock)
  and runs only with `TEST_DATABASE_URL=postgres://… npm test`.
